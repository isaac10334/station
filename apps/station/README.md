# Station application

One private application workspace owns the browser UI, development API, and
Electrobun desktop entrypoint. Run the usual `bun run dev`, `typecheck`, `test`,
`build`, and `desktop:build` commands from the repository root.

| Directory | Responsibility |
| --- | --- |
| `src/core` | Pure asset/workspace shapes, docking policy/reducer and validated source/package/theme data. Persistence/migration ownership is in the workspace application feature. |
| `src/contracts` | Private host-side AI, Component invocation, and worker transport contracts. |
| `src/providers` | Loop Kit provider implementations, AI conversation execution, Component inspection and execution. |
| `src/features` | [Feature entrypoints and ownership](src/features/README.md): injected controllers, pure projections, contracts and infrastructure within this package. |
| `src/services` | Editor sessions, builds/language workers, grants, guest RPC, and package orchestration. Effectful package services take explicit composition dependencies. |
| `src/ui` | React presentation, components, docking geometry/interaction, styles, icons and view state. |
| `src/application.ts` | Side-effect-free application factory: explicit storage/runtime inputs, provider registration, scopes and invocation lifecycle. |
| `src/composition.ts` | Browser bootstrap: localStorage, the one UI application, package runtime and sharing. Import `application.ts` from headless consumers. |
| `server` | App-origin API, cloud Component builds, and development server. |
| `desktop` | Native entrypoint, persistent installed resources, and updates. |
| `scripts` | App-owned build/resource/desktop preparation. |

Public identities and serializable guest types live in `@station/capabilities`.
The independently packable `@station/sdk` owns the guest connection. Host providers
are not shipped as part of either public package.

Workspace declarations and one lockfile live at the repository root. Root
`typecheck` prepares public package artifacts and compiler resources first, so it
does not depend on a previous development/build run. On a new checkout, run
`bun run desktop:prepare` once before checking the native entrypoint, as CI does. App scripts
resolve installed dependencies through package resolution, not a particular hoisted
`node_modules` layout. The development server runs with the repository watch root.
After moving a Windows checkout, regenerate dependency directories rather than
reusing absolute junctions from the old location. Stale per-workspace
`node_modules` directories can shadow a repaired root install; retain any needed
local links separately, remove or relocate the stale dependency directories, then
run `bun install --frozen-lockfile` and `bun run typecheck` from the new root.
After changing the public packages, rebuild them with `bun run build:packages`; embedded
guest compiler resources are regenerated by restarting `bun run dev`.

`bun dev` starts the development server on port 3000 (or `PORT`) with UI hot
reload and a companion Tailwind watcher. It explicitly uses development mode,
even if the parent shell has `NODE_ENV=production`; Ctrl+C stops both processes.
Use the exact URL printed at startup. `localhost` and `127.0.0.1` have separate
browser workspace storage. `bun start` is a separate server entry without the
development launcher or CSS watcher.

On Windows x64, scripting preparation automatically provisions the pinned
wasm-rquickjs 0.4.13 compiler from its official release when absent. Both the ZIP
and executable are verified by SHA-256; a verified cached ZIP works offline.
The cache is `%LOCALAPPDATA%/StationDevTools/wasm-rquickjs/0.4.13`. Optional
`STATION_SCRIPTING_COMPILER` selects an existing compiler with the same pinned
hash; a missing or mismatched explicit override fails without a download fallback.
PowerShell and the engine's pinned Rust toolchain are still build prerequisites.

Development Component artifacts continue to use the legacy repository `.artifacts`
directory. Installed desktop artifacts stay in the user's existing channel data
directory. Source moves do not rename storage keys, WIT IDs, asset IDs, or placements.

The headless entry is `createComposition(storage, createRunner)` from
`src/application.ts`. Creating and disposing it needs no DOM or React. Browser
execution and relative build URLs remain lazy defaults; a future command client
must supply its own runner and build transport plus persistence shared with the
running desktop. This change does not expose an unauthenticated command endpoint
or make browser localStorage available to CLI processes. Package runtime services
depend on explicit `PackageRuntimeDependencies`, never the browser singleton.
Recursive import tests guard these directions and public-package independence.


## Package development

This private application composes Station public packages and the four Loop Kit libraries.
Start with `bun run repo context @station/app --json` from the root.
See [architecture](../../docs/architecture.md) for internal layers, optional links,
resource ownership and retained security boundaries. `bun run repo verify @station/app`
checks its dependency closure; `bun run verify` includes all regressions and packed consumers.
The composition root owns startup/disposal; guest packages and transports cannot mint grants.


## Authored text and drawing editors

These are current host integrations, not proof that every editor is an installable
program. The [core-system review](../../docs/core-systems-review.md#creative-workstation-direction-2026-10-27)
records the bounded external-editor experiment and the missing inline editor
contract. Package source, installation, grants and running instances remain
independent even when official content eventually moves to separate repositories.

[Rich text authoring](../../docs/rich-text-authoring.md) covers Markdown/rich-note
assets, Notes widgets and expandable properties. The pinned BlockNote packages
are ordinary dependencies; the host provides controls and semantic theme tokens.

[VectorCraft integration](../../docs/artcraft-integration.md) uses an unmodified
pinned upstream web release. `prepare:web` runs `prepare:vectorcraft`; the first
run downloads the official archive into `.artifacts/vendor/` and verifies its
SHA-256. Subsequent runs verify the cache, rebuild the small Station wrapper and
stage vendor resources under `.runtime/vectorcraft` and `dist/vectorcraft`.
Desktop preparation copies the same resources; installed-native acceptance is
separate. Do not replace upstream files with a local fork or expose native RPC.
