# Current architecture

## Desktop distribution

The Windows Electrobun app packages the standalone frontend, Bun backend,
Component worker and pinned translator. `station-server.ts` owns the shared
app-origin API handler; `server.ts` supplies development resources and
`desktop/main.ts` supplies installed resources and persistent user artifact paths.
The desktop uses a fixed loopback origin and sandboxed native WebView2 without
native RPC. Canary updates download automatically and apply only on explicit
restart; persistent data stays outside the replaced bundle. See [desktop](desktop.md).
## Local app

`server.ts` is a single Bun server bound to localhost. Bun serves `index.html` as a fullstack HTML route and bundles the TypeScript frontend in development. `bun run build` produces one standalone `dist/index.html`; Component builds require the Bun server. Workspace source remains in browser storage. The server accepts one source project at `/api/component/build` and stores verified Component bytes under `.artifacts/` by SHA-256 for download.

`src/main.tsx` mounts `src/workspace-app.tsx`. The app has a docked navigation panel, shared toolbar, and controlled `DockHost`. `src/docking/core.ts` owns a versioned grid/split/stack layout, typed host policy, migration, and atomic commands. `src/docking/react.tsx` renders the main, dashboard, sidebar, and bottom surfaces with one dnd-kit drag coordinator; drag state and dialogs are transient. The store in `src/model.ts` persists layout, active tabs, sizes, and browser view per workspace. Widget type is separate from instance ID, so the same built-in widget may be placed more than once. `src/asset-browser.tsx` presents a sidebar list or a larger grid/list and provides a Stealth context menu. `src/component-view.tsx` renders a Component inside a focusable dock panel. `src/web-content-view.tsx` edits local HTML/CSS/JS and runs it in a sandboxed iframe; authored web assets may also have dashboard widget instances. `src/dashboard.tsx` renders the dashboard grid and per-widget controls. `src/onboarding.tsx` provides local guest and demo entry only. Tailwind v4 and locally imported shadcn/Stealth components live in `src/components`, with shared helpers in `src/lib` and styles in `src/styles.css` and `src/tailwind.css`. `components/greeting` remains the Rust/WIT project. `src/composition.ts` connects the store to browser `localStorage` and registers the existing Component runner with the linked `@loop-kit/capabilities` and `@loop-kit/host` packages. It acquires a runner for each run and revokes its scope afterward. Data uses the `unit-workspace.v4` key and migrates older flat layouts. Asset source and panel placement belong to a workspace; Component grants and artifacts are specific to Component assets. Appearance and AI provider preferences belong to the app. AI settings are UI state, not an active service integration.

Stealth neutral tokens in `src/styles/stealth.css` drive light and dark themes; `src/tailwind.css` maps them to shadcn tokens. Fonttrio Technical supplies IBM Plex Sans for headings and body text and IBM Plex Mono for code. `bun run styles` creates `src/generated.css` and copies its font assets before the standalone HTML build. Dashboard widgets, including an optional GameKit Snake widget, are built-in React UI, not Component plugins. Eligible built-in widgets can float with stable panel IDs and return to a dock. Broader tiling presets and plugin surfaces remain [exploratory work](explorations/surface-system.md).

Docking policy is host-owned typed configuration. Main permits four leaf stacks, sidebar and bottom one each, and dashboard and each Layout subtree 100 slots. Required home and navigation instances cannot enter Layouts; the singleton Asset browser can move between main tabs, dashboard/Layout slots and docks. These required instances cannot float. The bottom dock retains an empty slot when its last panel leaves and has an independent visibility control. The shared main toolbar sits below its real tab rail, while split leaves own local rails. Layout and floating placement persist per workspace; surface visibility and bounded undo/redo history are session-only. See [docking system](../src/docking/README.md).

Station uses one v4 dock document. `panels` is the compatibility widget-instance table; `containers[instanceId]` references a Layout widget's owned subtree in the same document. `widget-catalog.ts` supplies reusable definition/provider/renderer metadata for built-in content, editor views and authored web widgets. Additional editor instances share underlying source, while presentation and section state remain independent. Moves retain the ID and configuration; swaps validate both directions. Validation checks the entire ownership graph, unique placements, required instances, active tabs, normalized ratios, limits and cycles. Migration repairs v1–v3 trees and retains serialized `stack` widget IDs while replacing canned content with real children.

Grid nodes order bento rows; split nodes determine resizable columns and rows within each backing group. The host supplies a 380 px row extent (480 px below 640 px), with overflowing content scrolling inside its slot. Those extents are presentation policy, not separately persisted widget coordinates. Horizontal splits present vertically on narrow screens without rewriting the saved axis. Resize ratios are normalized, bounded to 20–80%, and undoable. Empty slots are intentionally retained. Removing an occupied slot is rejected; removing a Layout promotes its direct children to the dashboard in one recoverable command. Removing an instance keeps its source content; deleting content removes all its instances and clears layout history.

Widget headings pick up after 6 px of mouse/pen movement, or a 400 ms touch hold within 6 px. Touch pickup continues in the same gesture. Space/Enter picks up directly; arrows navigate destinations, Enter commits, and Escape cancels. Edit widgets exposes removal controls with static outlines; Done or Escape exits editing. Tabs expose inactive children, which retain a metadata preview until visible. `DockHost.widgetDragMode` selects physical or badge pickup globally or per instance, with a per-handle override. Physical pickup translates the existing live presentation and Layout descendants, leaving a placeholder without cloning or remounting content. Occupied single-instance slots swap on release; Alt joins tabs, Shift requests the nearest split edge. Previews never change persistent placement; a successful move commits one command/history entry. Automatic drag scrolling stays disabled.

`docking/presentations.tsx` mounts each instance once in a persistent host layer. Backing slot anchors supply bounds, clipping and input eligibility. Batched DOM measurements update frame styles directly, without rerendering widget content on scroll; nested frames predict owner translation in the same frame. Geometry observation ignores its own writes and unrelated animation/scrollbar styles. Stealth ScrollArea provides native viewports and thin overlay bars for the dashboard, widget content/settings and asset editors. Content owns its wheel gesture through its scroll boundaries; heading/background wheel input forwards once to the backing viewport. Focus restoration uses nearest-edge scrolling. Edit mode uses static outlines so content and scrollbars stay still. Transfers change geometry rather than DOM parentage, retaining editors, iframes and Component view services. Inactive tabs stay mounted, hidden and inert. Carousel children stay mounted and may be visible during native horizontal scrolling, but only the active child is interactive; settled scrolling changes the active ID. Reload and workspace switching create a fresh execution session. Source edits still invalidate artifacts or update authored widget documents. Weather requests location only when pressed; built-in content remains distinct from Component authority.

## Workspace search and navigation

`workspace-search.ts` derives one live catalog of authored assets and existing panels. The Stealth command palette searches it alongside app actions. Ordinary queries search all groups; `assets:` and `panels:` narrow content, `actions:` or `>` select commands, and `search:` selects both content groups. The main search control opens this same palette in content mode. Matching includes asset descriptions and Component filenames, but does not index source file contents. No second search dialog exists.

The existing required navigation dock panel renders `components/workspace/workspace-navigation.tsx`. Its per-workspace `navigation` preference stores query, source/asset-type facets, ordering, explicit pins, and exclusions. Missing preferences migrate to asset results with Overview and Asset browser pinned. Pins bypass matching, while exclusions win; missing references simply do not render. Dropping a local asset onto navigation pins it, and the filter editor supplies a keyboard-accessible pin picker. Removing a navigation entry only excludes the reference. These preferences are independent of structural layout history. Navigation remains the host-owned singleton in the side dock, not a new general-purpose or guest widget type.

Reusable built-in shell components live in `src/components/workspace`; interaction primitives live in `src/components/ui`. See the [component inventory and styling conventions](../src/components/README.md). Toolbar buttons share `IconAction`/`ActionTooltip`, including composed menu triggers.

## Web content path

### Asset terminology compatibility

The current model uses `Asset`, `ComponentAsset`, `WebContentAsset`, `assets`, and `selectedAssetId`. Loading the existing `unit-workspace.v4` key accepts legacy `units` and `selectedUnitId` fields. Dock migration maps the old `unit` kind and `unitId` field, plus browser/editor panel references, to asset terminology across tabs, nested containers, floating positions and maximization. Subsequent saves emit current model fields. Authored source, HTML, revisions, instance IDs, grants and artifact metadata are preserved. Historical storage/session/game keys, external project names and the versioned `unit:workspace` WIT/capability namespace remain compatible. They are identifiers, not current product vocabulary.

Asset types beyond Components and web content, installable editors, packages, theme assets, AI services and remote machines are [proposals](explorations/assets-and-programmability.md), not implemented behavior.

Web content assets persist one authored HTML document locally. Their editor and dashboard placements use `srcDoc` iframes with `sandbox="allow-scripts"` and no `allow-same-origin`, so script runs with an opaque origin and cannot read the host DOM or storage. A CSP meta policy placed before authored markup denies external scripts, resource loads, connections, forms, objects, and child frames in the authored document; it permits inline script and style for small widgets and data images/fonts. There is no `postMessage` bridge. Dashboard iframes fill the available slot below their heading. Overflow inside authored documents belongs to the iframe; the host cannot replace its scrollbars with Stealth ScrollArea without adding code or styles inside the isolated document. Preview reload is explicit during editing; dashboard widgets run the current saved source.

The Bun server rejects `/api/*` requests with a foreign or `null` Origin, rejects cross-site Fetch Metadata, and requires the exact app Origin for mutating requests. These checks protect Component build and artifact routes from opaque iframe requests. The app is still a localhost, single-user application: its API is not authenticated for remote deployment. A CSP on a `srcDoc` document does not guarantee that a navigated iframe keeps that policy, so this initial web asset must not be represented as a network-proof marketplace runtime. Marketplace content needs separate-origin serving with response headers, navigation and communication rules, backend authentication, resource limits, and review before installation.

## Capability host and inspector

`composition.ts` owns one application-wide Loop Kit host, a named application scope, and one child scope for every saved workspace. The store reads all saved workspace data at startup; creating a scope neither mounts that workspace's UI nor runs its assets. An inactive workspace can have a real, idle ownership scope. Providers register on the application host, not on individual scopes. Acquiring a capability asks its provider to create a fresh service instance owned by the requesting scope; merely defining or registering a capability creates no instances. Workspace renaming updates display metadata. `openScope(workspaceId, name)` binds a consumer to one workspace through a private WeakMap and places it under that workspace's scope. Built-in clock widget acquisitions and Component invocations have their own child scopes; finishing or unmounting revokes them. All host scopes, including idle workspaces, are reflected regardless of asset selection. Scope IDs and acquisitions are session-local and never persisted. Parent revocation cascades to descendants; providers remain available to other scopes. The inspector reads cached, deeply frozen snapshots through a subscription; reflection exposes no provider values or lifecycle controls. Completed scopes/acquisitions are removed after cleanup, with no retained activity history.

`workspace-capabilities.ts` defines trusted built-in JS capabilities: a wall clock with abort-owned timer subscriptions, bounded local SHA-256 text hashing, and a read-only workspace asset catalog. Catalog instances use the private scope binding, never a diagnostic name or parent ID, to select the workspace. Results contain only immutable names, IDs, kinds and revisions, with no source, settings or grants. These implementations check cancellation on operations; these checks supplement Loop Kit's cooperative lifecycle. The existing profile-specific Component runtime provider retains its identity and worker boundary.

The capability inspector has three tabs: Capabilities, Scopes and Grants. Capabilities combines definitions and provider implementations in a namespace → contract package → capability/version tree. Full capability IDs and provider names remain visible in collapsed rows. Expansion shows the definition, exact-version implementations, their scope uses, and bounded test actions. Scopes shows the same capability/provider presentation for each owned acquisition; subtree counts include creation and cleanup, and empty subtrees are labeled idle. Provider attribution joins by acquisition identity, so a removing registration and its replacement never exchange ownership in the UI. Shared presentation lives in `capability-inspector.tsx`; pure snapshot joins and scope counts live in `capability-inspection.ts`. These groups come from existing `namespace:package/path` IDs, not npm package names. Station documents its built-in JS contracts with `Host.define()`; definitions can exist without a provider and survive provider removal until host disposal. TypeScript members are not inferred at runtime. Clock, digest and catalog test actions end their scope in `finally`. Only the runtime provider directs users to the Component editor's verified build/run flow; other contracts without an inspector action retain their own consumer flow. Grants explicitly lists all Components in the current workspace, without selecting a fallback asset. The inspector and Component editor share `component-grants.ts`. Grant edits still go through the store and cancel an active run when a required grant is revoked. Built-in JS capabilities are not new WIT imports and are unavailable to authored iframes or Components. Scope names/parentage express lifecycle ownership, not permissions.

## AI chat and widget grants

AI chat is a built-in React widget available from Add widgets. Each mounted instance starts with no grants and no transcript. Users explicitly grant Gateway access, source-free asset listing, asset source reading, or web draft creation. `ai-tools.ts` maps these operations to validated AI SDK tool schemas; only granted tools are advertised. `widget-grants.ts` checks acquisition and retained method calls and revokes owned Loop Kit scopes. Widget removal, workspace switching, settings changes and grant edits cancel active work. Grant changes reset model history; they cannot retract data already sent. These are application permission checks for trusted built-ins, not isolation for arbitrary React or JavaScript. Existing built-ins retain their current authority; authored iframes and WIT imports gain no new access.

`ai-capabilities.ts` uses pinned AI SDK 7 with Vercel AI Gateway directly from the browser. Keys are user settings outside workspace persistence and tool results, held in memory by default. Remembering a key explicitly stores plaintext in a separate local-storage key; same-origin scripts can read it. The key is never added to prompts or tool output. The Gateway endpoint is fixed; there is no arbitrary credential destination. Each turn has a five-step limit, 4,096 output tokens and a 120-second deadline; prompts and source reads are bounded. User/model/tool conversation messages are retained only in the mounted widget. Every draft write requires inline source review, creates a fresh asset atomically, and neither places nor runs it. There are no AI delete, overwrite, execute, build or grant-management tools. Real model responses require a user-provided Gateway key and credits; test fixtures are not live inference verification.

## Component path

The asset browser keeps multi-selection as temporary view state. Toolbar, context menu, and Delete key actions confirm before one store update removes the selected assets and their dock panels. Each asset has an instance ID, including assets migrated from older storage, so a build finishing after deletion cannot install onto a replacement with the same slug and source.

`components/greeting` is an editable Rust/WIT source project. Its world exports `async run(string) -> string`, imports a P3 monotonic clock, and uses a host-provided future and stream in addition to logging and a bounded text surface. `bun run build:component` builds it with pinned nightly Rust and `wit-bindgen` 0.60.0 for `wasm32-wasip2`, inspects the resulting Component with Polyengine, invokes it, and embeds only sample source into the app. The target name does not determine the Component profile: inspected async types and `wasi:*@0.3.1` imports do. Rust's standard library also contributes recorded `wasi:*@0.2.12` imports.

`src/component-runtime.ts` selects the Polyengine provider for the inspected P3 profile, verifies downloaded bytes, and transfers them to a one-shot fixed worker. The worker checks the pinned translator asset hash, translates and inspects the bytes again, rejects unsupported imports, and instantiates with run-local WIT providers and Polyengine's minimal WASI capture/empty-filesystem provider. WIT grants are checked before execution and again at each workspace host effect. The host supplies a Promise and ReadableStream for the P3 future and stream; handles stay in the worker. The worker returns bounded plain results and effects, then terminates. Abort, grant revocation, source changes, deletion, and a 30-second timeout also terminate it. Loop Kit's host acquires and revokes the runtime capability; its signal is cooperative and does not enforce guest permissions. The worker is the hard stop.

`component-build.ts` creates a nonpersistent Vercel Sandbox from the pinned 30-day snapshot in `vercel-sandbox.json` for each build. It uploads the asset's Cargo lockfile, Rust, and authored/vendored WIT, runs nightly `cargo build --release --offline --locked --target wasm32-wasip2` with network denied, inspects the actual P3 world/imports, hashes the bytes, and deletes the Sandbox. The versioned manifest records a unique build ID, canonical source and WIT hashes, byte hash/count, inspected world/imports, profile, toolchain, snapshot ID, and translator hash. Wasm bytes are content-addressed; each build gets a separate immutable manifest even when different sources compile to identical bytes. This is recorded provenance, not a cryptographic build attestation. The client fetches and verifies the exact bytes before install and again before each run. Source edits invalidate the artifact; an instance ID prevents a deleted/recreated asset from receiving a prior build.

This locally authored Component path is not a marketplace security boundary. Wasm isolates guest memory, while the same-origin worker and import membrane limit authority. Polyengine does not claim hostile-guest confinement from provider checks alone. A separate-origin runner, tighter resource accounting, and a third-party iframe policy are required before untrusted marketplace Components are accepted. See [runtime measurements](component-runtime-profile.md).


## Component approval and desktop side dock

The Run tab requests missing Component authority through a modal approval dialog. Deny/dismiss does not invoke the runner. Allow once creates invocation-owned authority in `composition.ts`; it is never written to storage and expires in `finally`. Always allow atomically saves the existing boolean asset grants. Existing saved grants retain their meaning. Saved approval covers future revisions of that asset in that workspace; new grant IDs still require approval. Approval captures the displayed source revision and artifact hash, and rejects changes before invocation. The current P3 profile requires all four bounded imports.

`components/workspace/component-permissions.tsx` shares the grant ledger between editor settings and the capability inspector. Both show saved and active one-run authority and can revoke it. Store revocation notifications also fire when the saved boolean was already false, allowing cancellation of one-run approvals. All execution still validates source/bytes and uses the worker import membrane.

The desktop side dock stores `sidebarWidth` in the existing dock document (220–520 CSS pixels, legacy default 310). Its edge previews geometry during pointer movement, commits through `resizeSidebar`, supports arrow/Home/End keys, Escape cancellation, and double-click reset. Narrow screens retain mobile dock behavior and the saved desktop width.
